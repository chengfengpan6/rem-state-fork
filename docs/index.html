Scientific protocol and implementation choices

Protocol identifier: rem-prototype-0.1-iid-initialized-median90.

This repository implements an experimental instrument for studying inherited reliability maps. It does not establish that inherited maps help, harm, or persist in language-model teams. A successful live smoke run establishes a narrower fact: a specified model executed the declared sequence, produced the recorded outputs, and passed the reported engineering checks. Consult the run manifest for actual coverage and completion; a configured branch is not necessarily a completed branch.

1. Research question

The proposed study asks whether initializing an external memory with a team's interpretation of earlier evidence changes subsequent probabilistic judgments when the underlying observations and future evidence are held fixed. The memory object is a small context-by-source reliability map. It is not a complete transactive memory system, all organizational knowledge, or an instruction about whose advice must be followed.

Three links require separate evidence:

  1. Early random histories produce differences in the maps actors actually form.
  2. Inherited maps affect reported reliability beliefs, enacted cue use, or subsequent map updates.
  3. Those changes affect prediction quality.

Agreement is not accuracy, recall is not behavioral use, and a performance difference does not identify a unique psychological mechanism. These distinctions draw on research on transactive memory, organizational learning, and forecast evaluation [1–7, 10]. The experiment provides a controlled synthetic setting; it does not by itself establish effects in human organizations or deployed agent systems.

2. Research-design provenance and changes

The earlier research design specified three role-bearing actors, a 24-round common history, an 84-round future, and matched Team/Solo contrasts between an inherited map and an unknown map. The present prototype makes several previously unspecified choices and adds controls. These are transparent implementation decisions, not parameters established as optimal by the cited literature.

The context/truth change matters. If a fixed truth quota is known and past truths are observed, the prior for a later round can depend on the remaining quota. IID truth makes the .5 prior unambiguous. It sacrifices exact truth balance and is therefore not a literal replication of the earlier sequence design. The 24+84 configuration remains an offline candidate, not an authorization or validation of a full live study.

3. Synthetic task and oracle

Each round has a binary truth, a context, and three role-labelled binary signals. Conditional on truth and context, signal correctness is independent across sources. Reliability is stationary:

Context Source A Source B Source C
X .85 .65 .50
Y .50 .85 .65
Z .65 .50 .85

Each source has the same average reliability over balanced contexts. No source is best everywhere. A source's reliability is a property of its signal channel, not proof that the actor assigned to that channel is intrinsically more capable.

The generator fixes the complete event tape before actor calls. It samples independent Bernoulli(.5) truths and independent correctness draws under the matrix. Contexts occur once each in a shuffled three-round block. At the formal candidate horizon, this gives eight observations per context before the fork and 28 afterward.

The oracle computes the posterior probability of truth using the true reliability matrix and current signal vector. The matrix, oracle probability, future events, misleadingness statistic, branch labels, and researcher diagnostics are excluded from actor payloads. Actors know the task's IID truth rule and that reliability is stationary and context-dependent; they do not receive the reliability values.

4. State and information boundaries

Calls are stateless. The assembler supplies the permitted state explicitly:

Slot Content Important boundary
LE Observed contexts, role-labelled signals, and revealed truths No future outcomes or true reliability matrix
LB Forecasts and scores generated in the branch These are endogenous; they may differ after treatment
Pi The actor's own records and, where applicable, labelled founder records A new solo does not claim to have personally made the founders' predictions
H Current reliability map, unknown-valued map, or null Its lifecycle is part of the intervention

Past messages and private memos are archived but not restored into the next round. Forecast and score histories can nevertheless carry effects of earlier map exposure. Removing a named map field does not remove every possible causal carrier of that map's influence [5–7].

Matched branches begin with the same permitted pre-fork history. They reuse the same future exogenous tape and scoring rules. They are not required to have identical subsequent forecasts, scores, or updated maps: such divergence can be the treatment effect. Isolation checks must distinguish unplanned input differences from legitimate endogenous changes.

The no-peer-message architecture still has shared observations, shared branch behavior records, and a shared map. It is not an absence of every communication or social-information channel.

5. One round in each architecture

Interactive Team

  1. Each of three actors predicts privately using its current private signal and permitted history.
  2. The program discloses all three labelled signals mechanically.
  3. Each actor generates one bounded message without seeing the other actors' messages from that stage.
  4. Each revises its probability after receiving all three messages.
  5. The program takes the unweighted mean of the revised probabilities.
  6. Truth is revealed, scores are computed, and records are updated.

This entails nine successful model calls per round. It studies interpretation after mechanical disclosure, not voluntary information search or strategic withholding. Equal aggregation fixes the explicit weights on final actor forecasts; it does not fix how each actor uses the three sources [2].

No-peer-message

Roles, initial private signals, mechanical disclosure, revision, and final averaging remain. The middle stage produces a private memo instead of a peer-visible message. Revision receives only the actor's own memo. This preserves nine calls per round, but does not guarantee equal realized tokens or equal cognitive effort.

The private-memo substitution is an implementation choice. A literal deletion of the middle calls would be a different computational control. Neither comparison independently identifies common knowledge that the map is shared.

Full-information Solo

A separate single actor receives the complete signal vector from its first forecast stage. It produces an initial forecast, private memo, and final forecast: three calls per round. It is not three roles simulated inside one discussion, nor an average of three outputs.

At the fork, founder records from A/B/C remain explicitly labelled as historical records. The solo starts its own trajectory. Its exact information path and computation differ from the Team; the comparison is an architectural boundary, not a pure treatment of interaction.

Nominal team

Three full-information solo actors run separately, each with initial forecast, private memo, and revision. They share the exogenous tape and initial evidence, but cannot read one another's post-fork memos, predictions, or private map updates. Their final probabilities are averaged for scoring.

The implementation uses an independent Solo branch rather than reusing a nominal constituent. Nominal averaging entails nine calls per round. Score the average forecast itself; averaging the three individual losses answers a different question [8–9]. Separate instances are operationally isolated, but shared model and evidence can still produce correlated errors.

6. Map construction and treatments

Schema and formation

There are exactly nine (context, source) cells. Each numeric cell has:

estimate: a probability in [0, 1]
lower: lower subjective 90% uncertainty limit
upper: upper subjective 90% uncertainty limit
constraint: lower <= estimate <= upper

The uncertainty refers to source reliability, not an interval for the next binary outcome. A valid response contains no ranking instruction, deference rule, or prose lesson. The implementation does not claim that subjective intervals are calibrated confidence intervals.

The formation phase begins without a persistent public map. After the common history and its final feedback, the three actors independently report maps. The program computes the median of the three estimates, lower limits, and upper limits in each cell. This creates H0 without adding a model-based editor. It is a reproducible aggregation rule, not evidence that the actors reached consensus. The original individual reports remain available for analysis.

Four initial map conditions

Condition Fork input Meaning
H Agent-generated H0 Inherit the team's summary
E Code-computed map from the observed ledger Initialize using a reproducible evidence summary
RU The same nine-cell object with null estimates and limits Expose the actor to an unavailable-estimate object
R0 H: null No map object, while retaining the explicit state-slot interface

For E, each cell has a Beta(1 + correct count, 1 + incorrect count) posterior. The displayed point is its mean; limits are its .05 and .95 quantiles. It does not contain the true reliability matrix. Finite evidence can make this map inaccurate about the environment.

The point/interval schema aligns the display format across H and E, but subjective uncertainty and a specified Bayesian posterior are not psychologically equivalent. Their contrast initially identifies a summary-policy difference. Calling it pure interpretive distortion requires stronger evidence about display, provenance, confidence, and use.

Current limitation: R0 uses a null slot and no token-matching padding. RU is a larger structured object. The smoke therefore does not establish a length-controlled absence-versus-unknown effect. Token length, placement, and padding sensitivity require explicit validation before a confirmatory claim. Null is not converted to .50; any actual model response to it must be observed.

7. Two lifecycle modes

Default: initialized_update

The selected fork object initializes the current map. Subsequent calls read that current state. At update points, actors can reconstruct it from their allowed current state and accumulated evidence. Archived H0 is retained for researcher comparisons but is not separately replayed to actors.

This is mutable block memory, not strict one-time exposure. Before the first update, a numeric current map remains equal to its initial value and is repeatedly available. The prototype's scientific target is an initial-condition intervention in an external memory system.

All four map conditions have the same update opportunities. R0 and RU can acquire numeric maps at the first update; E is not automatically replaced by a fresh code posterior each round. Comparing a frozen H with continually refreshed E would combine different policies and would not isolate initial summary content.

The smoke updates after three future rounds. The offline 24+84 candidate updates every 12 future rounds. These intervals are explicit implementation choices, informed by cost and inspectability, not literature-derived optima [13].

Alternative: standing

The fork map remains unchanged throughout the future and no live map updates occur. R0 remains null. This mode tests continuously available fixed summaries and can support implementation checks against frozen-map reduced forms. It is a different policy from initialized-update, not proof of memory after the stimulus disappears.

Checkpoint ordering

At a scheduled checkpoint:

  1. Finish the round, reveal truth, and update event/behavior records.
  2. Clone the pre-update state for audits and probes.
  3. Run readonly measurements with no feedback or writeback.
  4. In initialized-update mode, independently obtain live map-update responses.
  5. Team/no-message: median-combine the three updates into one current map. Solo: use its own update. Nominal: keep each actor's update separately.

Measuring before the new shared median is displayed avoids treating immediate common exposure as evidence of independently shared beliefs. Audit responses are not reused as live updates. Updated maps and individual update responses are stored separately. Literature on temporal specification motivates explicit ordering, but does not prescribe this particular schedule [1, 4, 13].

8. Branch scope, probes, and execution status

The standard smoke configuration contains ten branches: Team H/R0/E/RU and Solo, no-message, and nominal H/R0. It is not a full four-by-four factorial. The presence of ten entries is a plan; actual successful branches must be read from the resulting run files.

The smoke uses three formation and three future rounds. It audits at the final future checkpoint. Its probe default batches the eight signal profiles for context X into one response per actor. A batch is a convenient diagnostic of schema and measurement routing. It is not eight independent interventions: the model sees the profiles together, and no complete three-context behavioral-weight claim follows.

The offline candidate requests fork and 12-round checkpoints and separate calls for all eight profiles in each of three contexts. Each independent profile starts from the same unchanged checkpoint state. That mode is restricted to offline execution in the current prototype. A configuration requesting it is not evidence that it has been run with live actors.

Source-list, actor-call, and message ordering use a seed-linked role permutation. This does not guarantee all occurrences of role labels are position-balanced: canonical JSON keys and map-cell ordering can remain fixed. A full positional-bias control needs additional prompt-level inspection and validation.

Branches run sequentially in configuration order in the archived smoke. They are not interleaved or randomized in execution time. The explicit actor payloads are controlled, but this does not control backend drift over wall-clock time. A later study should predefine branch-order counterbalancing or interleaving, record timing, and retain matched histories. This is a proposed implementation control, not a manipulation already performed by the smoke [13].

9. Outcomes and recommended analysis

The implementation stores realized Brier score (p-y)^2 and conditional Brier regret:

cBR = (p - p_oracle)^2

cBR is not the realized difference between two Brier losses on every outcome. The connection holds in the relevant conditional expectation under the oracle model. Proper scores evaluate probabilistic quality; they do not by themselves identify how relative source weights changed [10].

The recommended future primary direct estimand is the matched-seed difference in mean post-fork cBR between Team H and Team R0 under initialized-update. Team H−E and RU−R0 are key secondary policy contrasts. This is a recommendation, not a preregistered analysis or a result of the smoke. Primary/secondary families, inferential procedure, smallest relevant effect, missingness handling, and confirmatory sample size require a separate locked study plan.

Map error against the true matrix, divergence from the evidence-only posterior, adherence to initial H0, between-actor dispersion, and behavioral response surfaces answer different questions. No effect or no significant effect does not prove map non-use. The earlier sharedness prediction additionally required lower dispersion, greater proximity to H0, and greater distance from the evidence map after a corrective opportunity. Histories without such an opportunity must not simply be removed from performance analysis.

The signed history statistic M is computed from exogenous prehistory evidence, not from actor output. It is a candidate moderator and stratification variable, not a substitute for measuring the actual map. Both historical reference quintile means are negative, approximately −.713 and −.267; the latter is a less diagnostic region, not guaranteed overall misleading evidence or a guaranteed harmful map.

Fixed-map pseudo-weight models can be checked in standing mode. Their parameters cannot be carried unchanged into a model with endogenous Ht updates. Ledger-based estimation can also inherit uncertainty from a noisy first-stage estimate of ledger reading. Recovery under a scripted generating model is not identification in real actors [11–12, 14].

Behavioral analyses should preserve raw profile probabilities and separate overall response scale, relative cue profile, and interactions. Batched X-only smoke probes do not validate that measurement model. A future complete probe implementation should assess rounding, degenerate probabilities, additive-model fit, interactions, and whether reported reliability corresponds to enacted cue use.

10. Failure and reproducibility rules

Responses are strictly validated. The current implementation does not coerce malformed JSON, clip invalid probabilities, repair intervals, substitute .50, or silently retry failed model calls. The first provider, validation or budget failure stops the run and must be represented as failure or partial completion. Exhausted file-I/O recovery also stops dispatch. Researchers should not discard failures merely because they occur in a theoretically inconvenient condition.

Successful-path call counts exclude failures and any later policy changes. The same stage count does not establish equal realized tokens, cost, or reasoning effort. Runtime limits, actual model identity, backend metadata available to the adapter, raw responses, state hashes, and completion status should be reported from artifacts rather than inferred from a model name or configuration.

Evidence levels remain separate:

  • Scripted verification: known-answer checks of computation, routing, and state isolation.
  • Live smoke: a short execution of the declared workflow with a real model.
  • Technical pilot: enough complete trajectories to diagnose measurement, formation, errors, and cost.
  • Confirmatory research: a locked study with justified sampling, estimands, inference, and independent units.

A smoke cannot determine whether 180 histories are sufficient, validate a map-error mechanism, or estimate a reliable crossover. Sample planning should address both power and precision, with the actual dependence and error-control procedure [12]. The independent experimental unit is the matched prehistory realization, not the number of actors, cells, rounds, or probes.

Technical appendix: executable REM state-fork prototype

This appendix describes the implementation, not a completed confirmatory study. The authoritative specification for a particular run is its saved configuration and manifest. Small smoke runs test transport, state handling and traceability; they do not estimate population effects or establish a theory of team memory. See protocol.md for the scientific rationale and readiness.md for submission and evidence boundaries.

1. Task and data-generating process

Each round has a context X, Y or Z, a binary truth, and three labeled binary signals A, B and C. Contexts occur once each within shuffled blocks of three. Truth is independently Bernoulli(0.5) each round. Conditional on truth and context, signal errors are independent. The researcher-side reliability matrix is:

Context A B C
X 0.85 0.65 0.50
Y 0.50 0.85 0.65
Z 0.65 0.50 0.85

Respondents are told that reliability is unknown and stationary; the numerical matrix is not included in their task payloads. The deterministic generator uses a local pseudorandom stream seeded by the configuration. All branches of a seed receive the same future event tape. The full tape is a researcher artifact, not respondent input.

This implementation uses independent truths, not exact within-block truth quotas. It therefore must not inherit numerical results or oracle claims from another truth-balancing design. The known 0.5 prior remains appropriate conditional on past outcomes under this implemented generator.

2. State and information boundaries

The engine stores four slots and constructs an actor-specific view before each call:

Slot Meaning Visibility
LE Observed contexts, disclosed signals and realized truths Completed rounds only; shared evidence
LB Recorded final forecasts and scores Shared team history; nominal respondents receive only their own post-fork behavioral records
Pi Provenance-labeled personal/founder records Actor-specific view; no other actor's current private record
H Nine-cell source-reliability representation The actor's current map; may be absent or contain unknown cells

The map records an estimate and lower/upper subjective 90% uncertainty limits for each context/source cell. It contains no requested rankings or action recommendations. Valid map outputs must include every cell exactly once, with finite values in [0,1] and lower ≤ estimate ≤ upper.

All branches are deep-copied before any branch continuation executes. The engine constructs payloads from an explicit allowlist rather than serializing the whole run manifest. Branch labels, future outcomes, the true reliability matrix, history moderator M and oracle predictions are researcher-side objects. Hashes and saved checkpoints make the resulting states inspectable; their existence is not a substitute for an independent isolation check.

Solo and nominal respondents receive the common founders' pre-fork records as an explicitly labeled archive. Those records are not represented as the new respondent's own previous actions. Nominal respondents do not see one another's post-fork forecasts, private memos or evolving maps. Current messages are supplied only where the protocol allows them and are not appended to persistent conversation history.

3. A round and the architecture comparisons

Every round uses synchronous stages: all initial forecasts are collected, then all messages or private memos, then all final forecasts. Outputs from the same stage are not provided to later respondents in that stage. Truth is added to the observed ledger only after all final forecasts have been collected.

Architecture Initial information Intermediate step Final output Calls per round
team Own labeled signal All signals disclosed; each actor sends a peer message Three revised forecasts, equal mean 9
nomessage Own labeled signal All signals disclosed; each actor writes a private memo Three revised forecasts, equal mean 9
solo All three signals One private memo One revised forecast 3
nominal All three signals for each independent respondent Three separate private memos Three separate revised forecasts, equal mean 9

nomessage removes peer-message exchange within the round. It still retains shared evidence and, in mutable mode, shared median map updates; it is not a removal of every coordination mechanism. Equal stage counts do not guarantee equal token use or computation. Solo versus nominal additionally changes the number of forecasts averaged. None of these contrasts alone identifies common knowledge or a uniquely social mechanism.

Source-list, message and execution orders are recorded. A seed selects one of the six A/B/C order permutations. This does not establish that every label position throughout every serialized map and prompt is counterbalanced.

4. Formation, fork conditions and map lifecycle

A common team generates the formation history. Three independent map elicitations then produce the initial map H0 through coordinatewise medians of estimates and interval endpoints. This aggregation is an explicit prototype choice, not a validated psychological model of consensus.

The implemented fork conditions are:

  • H: initialize with the respondents' aggregated H0.
  • R0: initialize with an absent map, encoded as null.
  • E: initialize with a map computed from exactly the observed ledger, using a Beta(1,1) prior separately for each cell. Its estimate is the posterior mean; its interval is the equal-tail 90% credible interval.
  • RU: initialize with the nine-cell structure but unknown, null-valued entries.

E is an evidence-only finite-sample estimate, not the true reliability matrix. Its mathematical credible intervals and the models' subjective intervals share a schema but are not asserted to have equivalent semantics. R0 and RU differ in content and structure; neither contrast is claimed to match token counts or formatting perfectly.

Two lifecycle options are implemented. In standing mode the fork map remains unchanged. In initialized_update mode it persists until the configured update checkpoint, after which fresh respondent map elicitations replace it. The team and no-message architectures aggregate those maps by coordinatewise median; a solo uses its own readout; nominal respondents update independently. Thus condition labels describe initialization, not a promise that the R0 map stays absent indefinitely. Measurements occur after outcome feedback but before that checkpoint's map update.

The shipped short configuration uses three formation and three continuation rounds with a map update interval of three. Its terminal update is recorded, but no later forecast demonstrates the effect of that update. A longer design is needed to study repeated adaptation after updates. Other numerical settings must be read from the selected configuration, not inferred from this example.

5. Read-only measurement and scores

Map audits and hypothetical signal probes operate on disposable state copies. Their results are logged and are not written back into the running state. Before/after hashes check that the live state is unchanged. This is an engineering isolation property; it does not establish that the measurement perfectly captures the model's latent beliefs.

Batch probes present multiple signal profiles in a single call. They are diagnostics, not independent interventions on each profile. The short configuration probes the eight X-context binary profiles at its final checkpoint. A single-profile mode exists for offline exploration and is not enabled for live use in this prototype. No outcome feedback is provided for probes.

For forecast p and truth y, Brier loss is (p - y)^2. The researcher computes the exact conditional probability q from the known reliability matrix and the current signals. Conditional expected Brier regret is (p - q)^2; it is not the same as the realized difference between two Brier losses on one outcome. Recorded paired summaries are descriptive differences in mean regret within the same seed.

History metrics include M, strict reversal count and the worst pair concordance. Pairwise Beta ordering probabilities are computed as exact rational quantities for equal observation counts, so ties remain exactly one-half. M describes the sampled history; it does not measure the model's actual map error. This release does not fit w or lambda, perform causal mediation analysis, or produce confirmatory significance tests.

6. Model transport and replay

The live adapter requests gpt-5.6-luna through a ChatGPT-authenticated Codex CLI. It does not implement a public API-key transport. It checks subscription login and removes inherited OpenAI/Codex API-key environment variables from the child process. Availability, account limits and permitted access remain properties of that installed interface; the requested model name must not be presented as an independently verified server model fingerprint.

Each response uses a new ephemeral invocation in a temporary directory with task instructions and a JSON response schema. The adapter requests read-only execution, disables tools and host discovery features, and treats unexpected action events as failure. These measures reduce unintended local context and persistence. Host/server-added context is not fully observable, and subprocess isolation does not prove access to model internals or absence of provider-side state. The engine itself has no network or model SDK dependency.

The provider interface is complete(kind, payload, schema) -> response, with a trace exposed separately. Responses undergo strict validation. The harness does not clip probabilities, coerce values, repair malformed outputs or retry failed calls. A global cap counts dispatch attempts, including failed attempts. Cancellation prevents further dispatch; an already running provider invocation remains subject to its transport timeout.

Recorded replay feeds archived responses back to the engine and requires exact request-kind, payload and schema agreement. A successful replay establishes consistency of the saved inputs, responses and engine execution. It is not a fresh model run, and it does not establish that another account can access the same model or reproduce identical stochastic responses. Release verification should check request–response pairing, full consumption of the intended trace and equality of substantive outputs. Do not label replay as verified until that check actually succeeds.

8. Post-smoke file-I/O correction

The 342-response live run completed before a Windows checkpoint-replacement issue appeared during fast offline replay. That first replay stopped after consuming 252 archived responses; it made no model calls. Its failure is retained in evidence/verification_attempts/local_replay_01_failure.json.

The release adds at most five atomic-file replacement attempts when that specific operation raises PermissionError, separated by 0.05, 0.10, 0.15 and 0.20 seconds. Serialization, other exception types and model calls are not retried. Exhausted checkpoint recovery stops further dispatch and preserves the original error when failure reporting can still be written. The CLI reports the primary run error instead of masking it with an unused-replay-response check.

This is an engineering correction after data collection. It changes file-failure handling, not prompts, state transitions, outcomes or the experiment's scoring. The provenance file distinguishes the actual live-run code commit from the subsequent replay/release commit. Archived evidence bytes are exempt from Git line ending conversion, so their saved SHA256 values remain portable.

Proposed next measurement pilot: 7,314 responses, not run

The archived 3+3 smoke verifies a short execution. The next scientific need is to observe behavior after map updates and diagnose measurement, before any confirmatory study or 24+84 full design. The following is a concrete recommendation, not an accepted budget, preregistration, or evidence of execution.

Why the original budget cannot simply be inherited

The ten-branch, 24+84 offline candidate with fork and seven checkpoints, all map audits and independent probes of all 24 context/signal profiles requires 12,153 responses for one seed under this implementation. Running six such seeds would require 72,918 responses. A historical estimate of 6,000–8,000 total pilot calls cannot support that whole design. Model and execution continuity

For the first measurement pilot, retain the same requested GPT-5.6 Luna alias, low reasoning setting, explicit templates, and documented official transport to keep the comparison with the smoke interpretable. Record CLI version, execution time, available backend metadata, and actual tokens for every response. This is a recommendation, not a claim that an immutable model snapshot is available. A transport or model change requires renewed validation and must not be silently pooled with the earlier configuration. A call budget does not establish sufficient subscription allowance: 24+24 states are longer than 3+3 states, so smoke token usage must not be linearly extrapolated as an exact quota or cost estimate.

What this would and would not answer

The pilot can expose map formation, parser failures, probability rounding, post-update behavior, audit/probe consistency, practical token demand, and whether the proposed measurement scheme has usable variation. Six histories are not a defensible confirmatory sample or a well-powered test of M→H, mediation, crossover, or architecture moderation. E/RU observations on two histories are diagnostics. They must not be pooled with all six as if every condition had equal coverage.

Select no seeds by their model-generated maps or outcomes. Preserve all failures. Use pilot evidence to decide whether a larger measurement/recovery phase is needed, then separately plan the final 84-round study's independent sample size. This sequencing follows the distinction between verification and validation in Davis et al. (2007) and precision-based planning in Maxwell et al. (2008). Neither paper prescribes six histories, these checkpoints, or this call budget.

Readiness and evidence boundaries

This repository is an executable research prototype. A small real-model smoke run, offline tests, recorded-response replay and a journal submission are different deliverables. Each should be claimed only when its corresponding evidence exists. The scientific protocol remains a prototype specification, not a preregistered confirmatory study.

What the Organization Science call requires

The relevant journal is Organization Science, not Operations Research. Its official call listing links the seven-page special-issue CFP. These sources were checked on 19 October 2026.

Stage 1 asks for a roughly 3–5 page, 1,500–2,000 word proposal plus references, a technical appendix or supplement, and a Git repository or equivalent artifact containing a prototype or proof of concept (PDF p.3). It does not specify GitHub as the sole host or explicitly require global public access at Stage 1. The artifact must nevertheless be accessible for assessment. Final publication calls for a public GitHub repository or an accessible equivalent research object (p.4).

A repository therefore helps supply the research artifact, but does not replace the proposal, scientific contribution or technical explanation. This appendix describes the implementation; a submission appendix must additionally connect the implemented evidence, planned development, key risks and claimed contribution.

The general submission guidelines specify double-blind review. The special-issue PDF does not state an exemption or a special repository-anonymization procedure. A public repository for technical review and the eventual review package can be prepared separately; follow the actual submission instructions rather than assuming a named repository is automatically suitable for anonymous review.

The CFP specifies no named software license. Sharing should cover code and data the authors can legitimately distribute, with third-party material identified. It allows a differently focused longer paper elsewhere subject to copyright and duplicate-publication boundaries (p.6). The transparency policy additionally emphasizes accurate disclosure of research sequence, changes and AI use.

Required release checks

Before calling a release reproducible, check the following against that release's exact commit and configuration:

  1. Installation and offline tests work in a clean environment using the documented dependencies.
  2. Requests are paired with their responses and failures; records preserve the task inputs, schema, model request and available transport metadata without exposing credentials.
  3. Future truths, true reliability parameters, branch labels and researcher metrics are absent from respondent inputs. Copies do not share mutable state across branches.
  4. Audit/probe readouts leave live state unchanged, and checkpoint ordering matches the declared lifecycle.
  5. Exact recorded-response replay consumes the intended trace and reproduces substantive outputs. Timestamps and replay transport metadata may legitimately differ.
  6. Public files contain original/shareable code and synthetic-task research traces. Private correspondence, manuscript attachments, recordings, credentials and unrelated projects are excluded.
  7. A live run is reported with its actual transport and access requirements. If the adapter uses a subscription-authenticated Codex route, it is described that way, without inventing a public API endpoint or implying unlimited calls.

These are engineering release criteria, not extra requirements attributed to the CFP. They do not independently validate the theoretical interpretation.

Scientific work remaining beyond a smoke

The short configuration observes only a few rounds and a single sampled history. Its final map update is not followed by further forecasts. It cannot show sustained persistence, correction, adaptation after repeated updates, or a reliable relation between history M and actual map distortion. Batched probes are diagnostic and do not validate recovery of separate source weights or forecast scale.

Before a larger study, the map lifecycle, substantive estimand, interval interpretation, comparison architecture and measurement procedure need calibration. Real-model pilot data are needed to assess protocol compliance, map use, probability granularity, output variation, failure rates and costs. Confirmatory sample sizes and stopping thresholds must follow that work. Results from an earlier scripted surrogate or a different truth-balancing generator cannot be substituted for this evidence.

The repository deliberately separates an inspectable tool from a substantive empirical claim. A failed or null smoke can reveal an implementation or measurement boundary; a successful smoke shows that a particular technical path works. Neither outcome alone establishes that retaining a shared reliability map improves or harms organizational decision making.
